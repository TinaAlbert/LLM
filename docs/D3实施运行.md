## 本地配置及停止条件

在项目根目录的交互式 PowerShell 使用现有 Python（无需修改脚本执行策略）：

```powershell
.\.venv\Scripts\python.exe scripts\configure_guide_model.py
```

脚本隐藏输入 Key，只首次创建被忽略的 `.local/guide-model.json`，不输出秘密、不发 API 请求、不覆盖已有文件。已有配置请在本地编辑，不复制到聊天或报告。配置不是就绪证明：脚本保留空核查日期/来源、未核实的模型访问和额外费用；用户已有账号/余额的答复只证明这两项，不代表能力或完整计费已核实。

可信宿主 `ModelConfig.load` 严格检查 DS-1007 的服务、地址对应模型、版本和当日账号/价格核查。`account_review` 要求 existing_account、model_access、balance_available 均为真，checked_on 为实际核查日，evidence_ref 指向不含秘密的本地核查记录；`price_review` 同样要求当日来源、字符串形式的input_per_million="2"、cache_hit_per_million="0.04"、output_per_million="8"及经核实的额外费用上界。不能为通过检查虚填日期、来源、零额外费用或模型访问。密钥从该文件读取，不进子进程环境、模型输入、费用账本或日志。当前已有Key文件不被脚本覆盖；若模板补充缓存价字段，保留原密钥并仅在本地完成这项核查，不把旧核查日期自动续期。

完整输入上界需要对实际全部 messages、模板、特殊 token 和服务端固定指令成立。当前生产适配器没有可用的完整计数依据，`InputTokenCounter` 默认为空，会在预算预留和 HTTP 请求前停止。不能把字符数、UTF-8 字节数、别的模型 tokenizer 或测试中的计数替身改作生产依据。没有依据时，补 Key 仍不能运行真实模型。

首次技术费用账本初始化不是启动副作用。在完整隔离、模型能力、完整计费和输入上界都已核实时，由工程侧检查 `.local/guide-usage.json` 及其 `.initialized`、`.lock` 的历史，再调用 `BudgetLedger(...).initialize()`；三件中任一残留（含空锁）均拒绝初始化，不修补或重建。普通summary/reserve/settle/mark_unresolved/finish_first_round/receipt_snapshot只打开既有锁；缺锁、空锁或从未初始化时拒绝且保留三件字节/存在性。只有获准显式首次初始化使用排他创建，竞争失败不能擦除另一进程的预留。不删账本来恢复额度，不在本前置缺失阶段预先初始化。账本、初始化标记和锁锚点须一并备份；三件全部丢失时本地实现无法区分历史丢失与从未初始化，必须结合STATE中的首次记录、可信备份及账单恢复，不重新当首次初始化。accounted_cny是按批准高峰价和可信usage核算的上界，不冒充供应商实际账单。预留、物理次数和未决记录跨会话/重启延续；未决费用须凭可关联的可信 usage/账单核实，不能填零或自动重试。

完整计费依据的最新读取与恢复缺项统一见[服务核查](D3-10服务核查.md)。以下为2026-10-07审查依据：[官方token说明](https://api-docs.deepseek.com/zh-cn/quick_start/token_usage/)给出近似字数换算和离线tokenizer，[官方recipe](https://github.com/deepseek-ai/deepseek-recipe/blob/main/docs/tokenizer.md)提供请求转换/模板编码，两者没有承诺生产API完整计费输入一致性。[公开issue](https://github.com/deepseek-ai/deepseek-recipe/issues/5)有报告者的特殊文本计数差异，属于报告者实测，未由本项目收费重现，不作为已确认的全部服务算法。恢复需要匹配当前实际模型修订的服务模板/特殊文本和JSON Object附加输入上界证据；计数器须锁定证据哈希、实际完整messages、非思考与JSON模式并离线验证反例。仅response.model等于deepseek-flash不能证明同别名后台修订未变；官方system_fingerprint也没有公开的完整版本映射保证。已知供应商映射变化就停止，不能声称当前代码能检测全部内部漂移。

同登录内请求标识只保留最多800条参数摘要及匿名委托引用，用于丢响应后仍拒绝同标识异参数/已结束重放，退出和服务关闭清理；不保存旧候选、目标或反馈。每委托仍最多100个标识、8活跃委托/4合并等待者。整体30秒截止从POST到达开始，含最多3秒读请求体，不能读完后重新计时。自然语言金额过滤增加Unicode规范化/数字属性及英文常见数词反例；它不能证明任意文字语义正确，模型正确性仍须独立验收，程序过滤拒绝也计入基线组结果。

## 首轮基线与独立判定规程

实际模型验证尚未运行。恢复后先建立小规模首轮方法记录，不把 50/100 物理请求上限当作样本计划，也不预填 Q5 阈值。每条记录先冻结合成目标、V1知识/入口/Prompt版本、场景初态及事件、固定的用户反馈规则和独立终态判据，再按场景 §19.5 比较指引组、B0、B1：

- B0 只获得同一目标、V1资料及按统一规则产生的用户报告，不获得实时状态；缺状态是信息条件，不能暗中修补。
- B1 获得同样内容及当前允许的匿名单对象投影；指引组按已实现委托、观察、过滤和交付链路运行。相同模型/参数、预算、事件和反馈规则，信息差异仅限 §19.5。
- 不向任何组提供独立 SQL、隐藏状态、正确下一步、题号或固定答案金额。程序拒绝、未覆盖、预算停止和失败都计入对应组结果，不用可控响应替代真实失败。
- 正常个人路径、已有有效进度及偏离恢复、未知/未覆盖、付款未确认和已付无票分别保留真实轨迹；用户说完成、付款成功或模型自评不能代替票据终态。

独立工程连接复用原有效票、唯一付款/出票任务、冻结金额/扣款及库存判据。拒绝/失败分别比较原 23 类业务表；认证记录和新技术费用账本单列。原 demo 和两券空间只重读，不重新出票；新业务动作仅在串行、受保护 test 初态中执行。

业务负载按同环境、相同夹具和相同原业务请求序列分别执行“关闭指引”“启用但无任务”“真实指引进行中”，逐请求记录延迟/错误、PG连接与事务占用以及模型/过滤/交付耗时。无任务必须实测零模型调用；进行中必须实际模型工作，不用 sleep 代替。尚无完整模型前置时保留未测，不把前两组或线程设计推断成零影响结论。
