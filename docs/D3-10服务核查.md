## recipe 审查：已找到什么、仍缺什么

[官方 README](https://github.com/deepseek-ai/deepseek-recipe)描述的是请求转换、Prompt 编码与响应转换组件，推理后端及 HTTP 传输由外部提供；它不是当前官方生产计费服务的全部实现保证。[tokenizer 指南](https://github.com/deepseek-ai/deepseek-recipe/blob/main/docs/tokenizer.md)提供 `DeepseekV41Encoding` 和 `static/tokenizers/v41/tokenizer.json`，强调匹配模型与特殊 token；渲染后的 Prompt 再编码，不能只计两条消息的 content。

本次直接读到以下官方源码。它们只作为计数方案的待审查依据，不进入运行模型知识：

- [V4.1 编码实现](https://github.com/deepseek-ai/deepseek-recipe/blob/main/deepseek-recipe-encoding/src/v4/dsv41.rs)：非思考与思考模式的模板分支不同；不能用默认思考模式的编码结果替代本项目模式。
- [共享渲染实现](https://github.com/deepseek-ai/deepseek-recipe/blob/main/deepseek-recipe-encoding/src/v4/mod.rs)：`JsonObject` 会给首条 system 消息附加格式指令与 JSON 格式描述，并加入 BOS、角色标记及 assistant/非思考结束标记。因此，仅本地 SYSTEM_PROMPT 加 user 序列化文本的 tokenizer 结果不是完整 recipe 输入。
- [tokenizer 实现](https://github.com/deepseek-ai/deepseek-recipe/blob/main/deepseek-recipe-encoding/src/tokenizer.rs)：整体渲染结果通过 `encode(text, false)` 编码。该调用行为本身没有给出所有用户特殊字面量与线上 API 一致的证明。

以上读取的是 `main` 路径；GitHub 页面未显示可确认的最新 commit，公开 commit API 本次工具无法访问，**本次没有核实当前 main 的不可变 SHA**。不能拿下述报告者曾使用的 SHA 当作本次源码或线上修订。未下载 recipe/tokenizer，所以没有编造本地供应商文件哈希，也没有安装包或改变 Python 锁。

[官方仓库 issue #5](https://github.com/deepseek-ai/deepseek-recipe/issues/5)由外部报告者在 2026-09-11 提出，描述 `deepseek-recipe==0.1.1`、commit `8cadfede7063c896b944e7bae05daa3549ae97ea` 对用户特殊 token 字面量的计数低于其 API 返回计数；相邻重复 DSML 也使简单清空 added_tokens 的解释不足。2026-10-08 可见页面仍 Open、无维护者活动。该条是报告者对自身实验的原始报告，**不是官方确认或本项目收费复现**，也不证明线上完整算法；因此不能据它创造固定补偿量或把所有文本按字节计数。

对本项目实际生产路径，仍缺以下证据：

1. 当前 `deepseek-flash` 线上服务修订与可固定的 tokenizer、请求转换、模板版本之间的对应关系。
2. 非思考、无工具、JSON Object、文本 system/user 模式下，全部服务固定输入及 JSON 附加输入的计费规则或有依据的最大值。
3. 用户/知识/事实内容中的特殊字面量、Unicode、组合/控制字符及边界拼接经过服务处理后的完整计数规则，或者适用于全部允许输入的可证明保守上界。
