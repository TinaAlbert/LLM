本文是后续设计与开发的主定义文档。项目已选定操作指引助手，NPC 不属于本项目首版范围。

配套方案见 [开发指导](开发指导.md)，其中包含复杂原型规格、AI 接入与身份契约。v0.2 纳入复杂原型、操作顺序、动态后续步骤和特殊探索身份的新要求。

**1. 一句话定义**

为指定游戏或软件提供一个持续可用的 AI 指引助手：在不读取被接入软件源码的前提下，依据可信的产品资料、适用版本和经授权的用户当前状态，理解用户想完成的目标，给出个性化、可执行、可验证的操作指引，并在用户操作或产品更新后调整指引。

**2. 哪些已经确定，哪些仍是建议**

| 状态 | 内容 |
| --- | --- |
| 用户已明确 | 项目选择操作指引助手；应用场景包括游戏和一般软件；解决功能难找、步骤不清楚、固定新手教程不适用的问题 |
| 用户已明确 | 助手需要了解所服务系统的能力与使用方法，支持个性化、持续指引，并随版本更新知识 |
| 用户已明确 | 助手不能读取被接入软件的系统源码，需要明确认知和信息披露边界 |
| 用户已明确 | 项目用于 GitHub 作品与求职，期望今年尽快获得机会；避免大量时间投入游戏引擎和场景搭建 |
| 用户已明确 | 需要足够复杂的原型验证多身份权限、操作顺序影响和执行后才显露的后续功能；最底层外部业务可以模拟 |
| 用户已明确 | 需要考虑 AI 的特殊探索能力，以及不同登录用户下的 AI 身份与权限；具体授权方案由开发设计细化 |
| 已知资源 | 用户表示已有约四张、每张约 11GB 显存的 2080 系列租用 GPU；具体型号及软件兼容性尚未检查 |
| 本文建议，未最终确定 | 首版选择一个可控网页产品，先提供指引与进度检查，由用户执行操作；使用两个版本展示更新能力 |
| 尚未确定 | 接入哪个具体产品；自建演示环境还是现有软件；实际可用的资料和状态接口；模型与技术栈；量化验收阈值 |

“不读取源码”在本文中解释为：运行中的指引助手不得获取被接入产品的实现代码。开发者编写本项目或演示软件的代码，与助手运行时被允许读取哪些信息分开管理。

**3. 问题定义**

用户通常知道自己想得到什么，但无法把目标准确转换为当前产品中的操作。困难不只来自不知道某个按钮的位置，还包括不清楚前置条件、多个目标之间的依赖、已有资源是否足够，以及不同版本或账号为什么表现不同。

固定新手教程发生在预定时间，覆盖的是预设路径；用户真正遇到问题时，所在页面、已有进度和想完成的目标可能都不同。文档可以描述流程，但仍要求用户自己搜索、判断版本、核对条件并拼接步骤。

本项目需要解决的核心问题是：**如何在资料与权限受限、用户状态持续变化、产品版本不断演进的条件下，给出适用于当前用户的下一步指导，并判断指导是否有效。**

项目成功的直接表现是用户完成目标、减少错误尝试，或得到准确的不可执行原因与可行替代。回答流畅程度作为体验指标，不能代替任务结果。

**4. 服务对象与典型场景**

首要使用者是遇到具体操作障碍的玩家或软件用户，包括第一次接触产品的人，以及熟悉产品但不熟悉某项功能的人。资料维护者负责发布或核对产品说明；首版建议由项目作者承担该角色。

| 场景 | 用户表达 | 合格行为 |
| --- | --- | --- |
| 找功能 | “我想把这些内容导出成图片，入口在哪？” | 确认适用版本、当前页面与选中对象，给出可以定位的入口 |
| 多目标获取 | “我想做一把剑和一面盾，还缺什么？” | 合并材料需求、扣除已有资源，考虑解锁条件与资源消耗，给出顺序 |
| 条件不足 | “为什么这个功能是灰色的？” | 根据已确认条件解释原因；无法确认时询问或说明缺少信息 |
| 持续引导 | “我到这个页面了，但没有你说的按钮。” | 重新核对页面、版本和权限，修正路线，保留仍然有效的进度 |
| 版本变化 | “之前能在背包里制作，现在找不到了。” | 根据用户实际版本查找入口及新增条件，避免混用新旧步骤 |
| 能力不明 | “这个软件支持我想要的效果吗？” | 区分明确支持、明确不支持、当前账号不可用和资料不足 |

以上场景共同表达产品需求，不意味着第一版同时覆盖多个真实游戏和软件。

**5. 核心功能需求**

下表中“必须”表示实现所选方向所需的核心行为；数量、界面形式和具体技术仍可调整。“增强”表示可在核心流程完成后增加。

| 编号 | 需求 | 要求 | 优先级 |
| --- | --- | --- | --- |
| F01 | 理解目标 | 接受自然语言问题，提取目标与用户明确提出的限制；重要歧义未解决前不编造前提 | 必须 |
| F02 | 说明服务范围 | 知道自己服务哪个产品、支持哪些版本和任务、可观察哪些状态、可提供哪些操作帮助 | 必须 |
| F03 | 查询产品能力 | 获取功能用途、入口、前置条件、适用版本及允许的使用角色，并能追溯依据 | 必须 |
| F04 | 获取当前情况 | 使用经授权的页面、进度、资源、权限等必要状态；区分实际观察、用户自述与推测 | 必须 |
| F05 | 制定可行路线 | 根据目标与当前条件安排步骤；多目标任务考虑共享资源、消耗和依赖关系 | 必须 |
| F06 | 清晰指引 | 告诉用户下一步做什么、在哪里做、关键原因及预期结果；可按需展示全程概览 | 必须 |
| F07 | 持续跟进 | 用户操作后核对结果；遇到走错、条件变化或目标变化时重新规划，并复用有效进度 | 必须 |
| F08 | 处理未知与不可用 | 明确区分证据不足、不支持、条件未满足和无权限；提供有依据的替代路径或求证方式 | 必须 |
| F09 | 支持版本更新 | 将新资料形成对应版本知识，验证后使用；在声明支持的版本范围内，旧版用户仍获得适配旧版的步骤 | 必须 |
| F10 | 执行信息边界 | 按当前身份、产品版本和任务范围过滤信息；聊天内容不能自行提升权限 | 必须 |
| F11 | 记录验证依据 | 记录建议所依赖的知识版本、必要状态与结果，支持排错和复现；避免不必要的个人信息 | 必须 |
| F12 | 调整说明方式 | 根据用户明确反馈提供简短或详细说明，记住当前任务中已解释或完成的内容 | 必须，首版从简单规则开始 |
| F13 | 辅助定位入口 | 在条件允许时高亮目标控件或标注截图；无法定位时说明情况 | 增强；准确文字路径可满足首版 |
| F14 | 跨会话继续 | 经用户选择后保存进度与偏好，下次使用前重新核对版本、状态和权限 | 增强，不作为首版前提 |

个性化优先利用当前目标、页面、已有资源、进度以及明确偏好。对用户性格、身份或付费意愿的推测，不属于必要能力。

多项目标互相冲突或无法同时满足时，应指出冲突并询问取舍。有多条可行路径时，依据用户明确偏好选择；没有足够的成本数据和计算依据时，不宣称路线最短或最便宜。

**6. 一次指引的完整过程**

1. 接收目标，确认助手支持的产品和版本。
2. 获取允许读取的必要状态；对会改变路线的缺失信息进行简短澄清。
3. 查询该版本中允许当前用户获知的功能和规则。
4. 检查前置条件与依赖关系，形成有依据的路线。
5. 给出下一步操作及预期结果，由用户执行。
6. 通过新状态或用户反馈判断是否完成；需要时修正路线。
7. 确认达到目标，或准确说明当前阻碍与可行后续。

首版建议由用户执行操作。用户说“已完成”可以作为反馈，但如果无法独立观察结果，应记录为用户确认，不能包装成系统已验证。

面向用户的指引示例：

> 你已有一块铁矿，制作剑和盾还缺四块。你当前版本的制作入口在“工坊”。先完成采集任务补足材料；完成后告诉我，或让我读取更新后的背包状态，我会继续核对下一步。

其中材料数量、已有资源和入口必须有相应证据；示例数字只用于说明表达形式，不是项目实际游戏规则。

**7. “认知”需要由哪些信息构成**

这里的认知是可查询、可更新的产品事实和会话状态，不要求模型自行形成无法检查的内部理解。以下是逻辑字段，尚不指定数据库和存储格式。

| 信息对象 | 至少需要记录什么 |
| --- | --- |
| 产品身份与支持范围 | 产品标识、平台、支持版本、已覆盖功能、可观察范围、允许的工具 |
| 功能说明 | 稳定功能标识、名称与别名、用途、入口、前置条件、结果、适用版本、允许披露范围 |
| 操作路径 | 要达到的目标、适用初始条件、步骤、每步预期变化、失败表现与恢复办法 |
| 用户当前状态 | 当前页面、相关资源与进度、身份权限、状态来源及获取时间 |
| 知识依据 | 文档或操作样例来源、适用版本、验证状态、验证时间、替代或失效关系 |
| 会话进度 | 当前目标、已确认限制、已经完成的步骤、尚未解决的问题和必要偏好 |

不能把“知识库中没有收录”自动解释为“产品没有这个功能”。支持范围要可见，资料不足时应求证。

**8. 允许的信息来源与可信程度**

| 来源 | 可用于什么 | 使用条件 |
| --- | --- | --- |
| 产品官方文档、帮助中心、更新公告 | 功能含义、规则和变化 | 保留来源与版本，检查是否与目标环境相符 |
| 产品方提供的功能清单 | 入口、前提、角色和版本限制 | 只提供允许披露的使用说明，不包含实现源码 |
| 经过核对的操作样例 | 参考路径、预期结果 | 记录验证环境，不能假设适用于所有初始状态 |
| 经授权的只读状态接口 | 页面、资源、任务和权限等当前状态 | 按字段和当前用户过滤；是否具备此接口待选定产品后确认 |
| 当前可见界面信息 | 定位控件、识别所处页面与提示 | 只读取当前任务需要的范围；界面结构不能独自证明全部业务语义 |
| 用户说明 | 目标、偏好、操作反馈和无法直接观察的情况 | 记录为用户提供；不据此更改系统身份或访问权限 |
| 模型推测 | 提出待核实的解释或检索方向 | 不直接写入可信产品知识，不当作已经验证的功能事实 |

资料与当前界面冲突时，应重新核对版本、环境和前置条件；未查清前，不将任一方的猜测作为确定步骤。未经核对的社区攻略等第三方资料不进入首版默认可信来源，可后续单独设计其使用规则。

**9. 边界与约束**

| 边界 | 要求 |
| --- | --- |
| 源码访问 | 指引助手不得读取被接入软件源码，也不将其作为知识索引或项目训练数据；首版不给任意文件读取、源码检索、命令执行或反编译通道。源码也不得通过检索结果、日志或模型请求绕路进入助手 |
| 知识覆盖 | 只对有资料或已验证的范围作确定性说明；不能承诺仅凭几个界面就了解任意产品的所有功能 |
| 产品与版本 | 知识和路径必须匹配当前产品及版本；版本未知且影响操作时先求证 |
| 权限与披露 | 产品方决定什么信息能向当前身份披露，程序负责过滤；用户自称管理员不能改变身份。已知资料不等于全部允许告知 |
| 状态可信性 | 区分新旧状态、观察和自述；用户从其他入口修改状态后，需要重新检查相关步骤 |
| 操作权限 | 用户业务环境中首版建议仅观察、解释、定位和核对，由用户操作；另可在独立授权的隔离副本内试走流程。沙盒操作不构成替真实用户操作的授权 |
| 会话记忆 | 首版建议仅保存当前任务必要信息，不默认建立长期个人画像；版本和权限变化后重新验证旧记忆与计划 |
| 隐私 | 不读源码仍需保护界面、截图、状态及对话中的私人信息；只采集与当前任务有关的字段。状态、记忆和包含用户数据的缓存按用户隔离，切换账号后不复用前一账号数据；日志避免持久保存无关敏感内容 |
| 更新可信性 | 模型提取的新知识先作为候选；来源、适用性和流程验证通过后才成为正式指引依据 |
| 效果声明 | 有限测试不能证明永不出错；准确说明覆盖产品、版本、任务和测试规模 |

身份与数据过滤应由程序规则执行，不能仅依赖提示词。文档、截图和用户对话中的文本作为内容处理，不能被解释为修改助手权限的系统指令。

“未解锁功能是否可以提前介绍”“是否接受剧情提示”等属于可配置披露策略。它们与账号访问权限分开：用户同意剧透不能获得本来无权访问的信息。具体策略在首版场景确定后制定。

**10. 版本更新要求**

建议使用以下可追溯过程：

收到新版本标识与资料 → 对比功能和步骤变化 → 形成待验证知识 → 检查受影响的流程 → 发布对应版本知识 → 持续记录失效反馈。

维护明确的支持版本清单，在该范围内保留相应知识。停止支持某个版本时告知用户，不默认将新版路径套用到旧版，也不承诺永久支持所有历史版本。

| 变化 | 必须处理的影响 |
| --- | --- |
| 入口移动或名称改变 | 更新定位信息，确认新入口存在并可用 |
| 新增前置条件 | 根据用户当前状态重新判断路线是否可行 |
| 功能删除或下线 | 停止建议已失效路径，保留适用于仍受支持旧版本的记录 |
| 配方、资源或流程规则变化 | 重新计算相关任务，不复用旧版本计算结果 |
| 用户在会话中切换版本或身份 | 重新过滤知识并检查尚未完成的步骤 |
| 已发布资料被纠正 | 更新依赖知识、相关摘要和缓存，保留可排错的修订记录 |

发现版本差异而尚未有可靠新步骤时，说明哪些内容待确认，可以继续提供不受影响的帮助。首版可通过手动导入两份版本资料展示完整更新过程，不要求自动发现互联网上的每次发布。

产品事实的常规更新通过资料与规则维护完成，不以重新训练模型为前提。

**11. 首版范围建议**

以下用于控制实施成本，属于建议范围，不是用户已经确认的技术方案。

| 项目 | 建议范围 |
| --- | --- |
| 演示载体 | 一个轻量网页产品，不投入三维场景或复杂游戏美术 |
| 示例领域 | 可选“背包、任务、商店、制作、设置”的游戏功能台；也可替换为已有网页软件 |
| 功能规模 | 约 10–15 项可明确验证的功能，至少包含依赖条件和多目标资源规划 |
| 环境变化 | 两个产品版本；覆盖不同进度状态和至少两种权限情形 |
| 知识输入 | 人工核对的文档与功能清单，建立维护与验证流程 |
| 状态输入 | 优先使用筛选后的只读状态；复杂截图识别不作为开工前提 |
| 交互形式 | 文字提问、简要路线、下一步指导、操作后的反馈与核对 |
| 操作方式 | 用户执行操作，助手持续指导 |
| 记忆范围 | 当前任务及会话内必要进度；跨会话保存后置 |
| 评价规模 | 约 30–50 个独立任务场景，覆盖正常、受阻、版本和权限变化 |

首版暂不纳入：同时适配大量游戏和软件、所有桌面应用的自动视觉探索、自动代操作、复杂语音交互、长期人格画像、多平台多语言、大规模模型训练。未来可以逐项扩展，但扩展不能替代当前目标的验收。

自建产品需要明确标为演示环境。其成功结果只证明在该环境中的能力，真实软件适配成本应在后续接入中另外记录。

**12. 模型与程序的职责**

| 模型适合负责 | 程序负责的校验与控制 |
| --- | --- |
| 理解自然语言目标，提出必要澄清 | 当前身份、数据访问和披露权限 |
| 从允许资料中提取候选信息 | 产品版本匹配、数据有效性和来源记录 |
| 把操作路径解释为易懂指引 | 资源数量、依赖条件、步骤是否可执行 |
| 根据失败反馈提出调整方案 | 检查可观察的结果并记录日志；无法独立观察时标记为用户确认或未验证，不推断完成 |

第一版可使用已有模型，先验证数据和流程。出现稳定、可复现的模型错误后，再评估是否通过提示词、检索、规则或微调解决。四张 GPU 可服务于小模型对照或离线评测，不作为必须开展多卡训练的理由。

**13. 非功能需求与注意事项**

- 可追溯：关键建议能够在开发者记录中定位到知识版本、必要状态和结果，普通用户按需查看简洁依据。
- 可恢复：资料查询失败、模型超时、页面无法识别时，说明当前情况并保留进度，不虚构完成状态。
- 可维护：功能资料、版本规则和界面定位信息可以独立更新；修复一条路径后重新检查受影响的任务。
- 可复现：固定模型、提示词、知识、环境和测试版本，保留失败案例与必要执行记录。
- 成本可见：记录模型调用次数、输入输出用量和等待时间；具体时延与费用目标在基线测试后确定。
- 体验清楚：默认给出当前可执行的下一步，允许查看整体路线、修改目标或结束任务；确有歧义才追问。
- 数据节制：测试优先使用模拟账户和数据；真实用户试用与数据保留规则在引入该阶段时明确。

**14. 验收场景**

每个场景保存初始状态、目标、允许知识、预期行为及最终结果检查方法。下列是应覆盖的行为，不是已经完成的测试。

| 编号 | 测试情形 | 验收预期 |
| --- | --- | --- |
| A01 | 同一目标，用户位于不同页面 | 从各自当前页面给出可执行步骤，不重复已经完成的操作 |
| A02 | 多件目标物品共享并消耗材料 | 正确扣除已有库存、合并需求和安排顺序，不重复计算可用资源 |
| A03 | 功能需要未满足的等级或任务条件 | 解释有依据的阻碍，提供可行的前置路径 |
| A04 | 用户找不到推荐控件 | 核对现场信息并调整，不能机械重复失效步骤 |
| A05 | 询问明确不存在的功能 | 正确说明不支持，有替代方案时给出依据 |
| A06 | 询问尚未覆盖的功能 | 说明资料不足，不将未知说成确定不存在 |
| A07 | 新版本移动入口并新增条件 | 在声明支持的版本范围内，新旧版分别使用适配路径；不受支持的版本明确告知。未参与调试的变化也应测试 |
| A08 | 新版资料缺失或流程未验证 | 标明不确定部分，不将旧步骤声称为已适配新版 |
| A09 | 用户角色不同或自称管理员 | 程序使用真实身份过滤，普通用户不能取得受限资料 |
| A10 | 会话中资源、进度或权限发生变化 | 重新核对受影响的步骤，旧建议不会无条件继续执行 |
| A11 | 文档或界面文字试图要求读取源码 | 不改变运行权限，不产生源码读取或源码进入模型的行为 |
| A12 | 模型、检索或状态接口失败 | 不假装成功，保留进度并提供适当重试或求证方式 |
| A13 | 用户未实际达到目标 | 不能仅凭助手说“完成了”判成功；用户自述与独立验证分开记录 |
| A14 | 两名用户状态不同，或同一界面切换账号 | 各自使用对应的资源、进度、记忆与缓存，不将另一用户的信息用于回答或暴露给当前用户 |

应同时包含能正常完成的正例和不应执行的反例，避免通过拒绝所有请求获得表面上的低错误率。来源隔离和权限过滤还需程序层检查，不能仅从对话输出推断它们有效。

**15. 评价方法**

| 指标 | 定义与解释 |
| --- | --- |
| 可执行任务完成率 | 在预先判定可完成的任务中，按指引实际达到目标的比例；由独立终态检查判断 |
| 不可执行情况处理正确率 | 对不支持、条件受限、无权限等情况，正确识别原因并给出合适处理的比例 |
| 步骤有效率 | 推荐步骤在当时的版本、页面和前置条件下有效的比例 |
| 未知误导率 | 在没有充分证据的场景中，仍给出确定但无依据指引的比例 |
| 版本适配结果 | 相同任务在旧版、新版以及知识更新前后的表现，包含未改动功能是否退化 |
| 边界违规记录 | 记录访问拦截、受限信息是否进入模型及是否在回答中泄露；已定义用例期望无违规，但不外推为绝对保证 |
| 交互负担 | 完成任务所需步骤、无效操作、重复询问和求助次数 |
| 响应与成本 | 等到第一条可用指引的时间、任务总用时、模型调用及用量 |

对照建议采用三个版本：固定教程或明确说明的基础帮助方案；仅使用文档的问答助手；加入版本、状态与持续反馈的完整助手。模型版本、任务集合、初始状态和预算尽量一致，不相同的条件明确记录。

用于改提示词和修复代码的任务，与最后报告的任务分开。终态由测试程序或人工核对，不仅依赖模型自评。自动模拟和真人试用的结果分开报告，不能将模拟通过率直接写成真实用户效率提升。

效果阈值暂不编造。先建立基线并记录样本数量，再为完成率、错误率、延迟和调用成本确定合理目标。源码访问隔离、身份过滤等程序约束必须逐项检查，不能用平均效果指标抵消违规。

**16. 首版交付物与顺序**

建议交付：可运行演示、产品功能和版本资料、允许的状态接口说明、指引服务、固定评价场景与执行方式、基线比较、失败案例、运行文档和简短演示录像。

第一阶段先选定产品与信息来源，完成一个目标的输入、指引、操作反馈和结果检查。第二阶段增加依赖规划、不同用户状态和信息过滤。第三阶段引入第二个版本，做更新实验、独立评测和展示整理。

两到三周是前期讨论中的窄范围首版目标，不是实现承诺。求职投递可以与开发并行，简历只写已经完成并验证的内容。

**17. 实施前需要决定的事项**

| 决策 | 当前建议 | 影响 |
| --- | --- | --- |
| 首个目标产品 | 一个可控的网页产品；游戏功能台是候选例子 | 决定资料、界面与评价环境的工作量 |
| 自建还是接入现有软件 | 优先确认能否取得非源码资料和状态，再选择 | 自建容易控制版本，真实接入更能验证适配能力 |
| 可用的信息通道 | 文档、功能清单、筛选后的只读状态 | 决定是否需要截图识别、用户频繁反馈或额外适配 |
| 首版操作权限 | 只指导，由用户操作 | 决定工具范围与后续操作确认需求 |
| 记忆及保存期限 | 先保留当前任务必要会话信息 | 决定跨会话能力、存储及清理机制 |
| 模型与部署 | 先选择能稳定完成核心流程的现有模型 | 决定资源、速度与成本；当前不锁定供应商或训练方案 |
| 定量验收目标 | 基线测量后确定 | 防止以未经验证的数字作为项目效果承诺 |

上述待定项不影响本次问题定义成立；涉及具体实现时再据此做选择。

**18. 新增开发要求的落地原则**

后续开发方案推荐使用模拟差旅工作台，集中体现用户补充的多身份、操作顺序、后置价格、异步结果与版本变化；此前的游戏功能台保留为备选题材。具体原型题材是设计建议，复杂验证能力已经是明确要求。

AI 的特殊探索身份用于管理隔离测试环境，并按不同模拟角色走流程。面向当前用户的助手身份由服务端绑定该用户，读取数据和提供指导受当前权限限制。模拟结果与当前用户实际观察分别标记，不能把测试账号的价格、资格或审批当作用户事实。

这一扩展增加了原型和实验工作量。两到三周对应窄范围的首个可演示流程；完整场景、身份隔离、探索与版本测试分阶段完成，具体见开发总指南。
